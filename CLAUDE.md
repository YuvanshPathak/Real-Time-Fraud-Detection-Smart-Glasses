## The one rule that must never regress

**Every identity check compares against the credential presented in that specific interaction — never a pre-stored personal reference.** No database, cache, or persisted biometric template may exist anywhere in this codebase. `/face-to-id-sync` is the correct pattern: it takes `live_image` and `id_document` as two fresh uploads in the same request. Liveness/spoof endpoints (`/face-check`, `/voice-check`) need no reference at all.

This was previously violated (a static `reference_faces/reference.jpg` and `reference_audio/reference.wav` were compared against on every check, plus an unused SpeechBrain speaker-embedding model, plus an orphaned ID-portrait crop written to `uploads/id_crops/` and never cleaned up) and removed for exactly this reason. If you see any new code writing a face/voice/document image to disk and reading it back on a later request, or comparing a live capture against anything not uploaded in the same request, flag it — it's the same regression. Corollary: uploaded files must not outlive the request that uses them; every route deletes its saved upload in a `finally` block.

## Current build status (verify before trusting)

All 5 detection/fusion endpoints work — confirm with `python backend/test_api.py` (note: this script doesn't actually exercise `/face-to-id-sync`, only `/`, `/risk-score`, `/face-check`, `/voice-check`, `/document-check` — verify that one manually if touching it). Fusion logic (`utils/scoring.py`) includes an escalation floor (a single modality failing its own 0.65 threshold puts a floor under the verdict, regardless of the weighted average) and renormalizes weights across only the modalities actually evaluated. `analyze_facial_liveness` gates on face presence (Haar cascade) before scoring. **New this phase**: `utils/session_log.py` persists verdict metadata (scores, risk level, evaluated modalities — never raw audio/images) to a local SQLite DB (`backend/session_log.db`, gitignored) on every `/risk-score` call; `GET /sessions?limit=N` returns recent history. `routes/voice.py` also has a **temporary debug-only** feature that saves a copy of every `/voice-check` recording as an MP3 to `backend/debug_recordings/` (gitignored) via `lameenc` — for manually listening back to confirm mic capture is real audio, not a permanent feature; remove it once no longer needed (see the comment block in that file).
- **Frontend (`frontend/`)**: built and tested. `RiskAnalysisCard` detects when its inputs go stale relative to the last fused verdict. `LiveFeedCard` no longer fabricates ESP32/BLE/camera telemetry that doesn't exist — labeled honestly as a browser webcam stand-in. Its voice recorder (`VoiceVerificationCard.jsx`) uses the browser's **default system microphone** (unconstrained `getUserMedia`), not any ESP32 hardware — if a recorded/debug-saved sample sounds silent, check the OS mic input level/device selection before assuming a code bug (confirmed via direct testing: the MP3-export code itself preserves amplitude correctly when fed real audio).
- **Firmware (`firmware/`)**: rebuilt from scratch 2026-08-21 as a PlatformIO project (previous Arduino-IDE-based `firmware/smartglasses/` implementation deliberately deleted — recoverable only from git history before that date). **Voice module is built and verified working end-to-end on real ESP32-S3 hardware** — on-device capture (`src/microphone.cpp`, ESP-IDF 5.x PDM RX driver) → Wi-Fi upload (`src/api.cpp`) → cloud analysis → fused verdict → LED display (`src/main.cpp`), confirmed via matching entries in both the serial log and the backend's request log across multiple sessions. **Known reliability caveat, not a code bug**: success is Wi-Fi-signal-dependent — on a weak/marginal link (confirmed down to -94dBm RSSI on one test network) uploads fail in varying ways (`HTTP -1` connection refused, `-3` mid-upload write failure, `-11` read timeout); `api.cpp` now retries once with a longer timeout (15s) per request, which recovers some but not all of these. A stronger, closer access point or hotspot fixes it outright. Uses the `pioarduino` fork of `platform-espressif32` (`platformio.ini`), not the official PlatformIO registry — the official one is stuck on ESP-IDF 4.4, too old for `driver/i2s_pdm.h`. `board_build.arduino.memory_type = qio_opi` in `platformio.ini` is the PlatformIO equivalent of Arduino IDE's "OPI PSRAM" setting — required or `psramFound()` reports false. Real Wi-Fi/backend config lives in `firmware/include/config.h` (gitignored, machine/session-specific — IP drifts with DHCP, re-check with `ipconfig` each session); `firmware/include/config.h.example` is the committed template. Camera, face/document capture, on-device feature extraction, and the phone Gateway relay are **out of scope for this phase** — voice only.
- **TinyML on-device extraction (`ml/`, `firmware/src/tinyml_features.cpp`/`tinyml_model.cpp`)**: 🟡 partially built, 2026-08-22. The full pipeline works — log-mel feature extraction (`ml/features.py`, mirrored in C++ via a generated header, `firmware/include/tinyml_feature_config.h`) → small Conv2D model → INT8 TFLite Micro quantization (`ml/train.py`) → on-device inference (`tinyml_model.cpp`, esp-tflite-micro) — but it's trained only on `ml/generate_synthetic_dataset.py`'s **fabricated** genuine/spoof signals, not real audio (see `ml/README.md` for why, and the "Retraining on real data" section for the actual next step once real hardware-captured samples exist). `main.cpp` runs it every cycle alongside (not instead of) the existing raw-audio upload; the resulting `tinyml_liveness_score` flows through `/risk-score` as **informational-only** (`utils/scoring.py`'s `informational` key) — deliberately excluded from `fraud_risk_score`/`risk_level`'s weighted fusion so the panel-verified voice pipeline's behavior is unchanged whether or not it's present. **Not yet compiled or flashed** — no PlatformIO toolchain was available in the environment this was written in, so `firmware/src/tinyml_model.cpp`'s exact TFLite Micro op-resolver list and tensor arena size are reasoned estimates, not confirmed against a real build; `pio run` is the first real test. Phone gateway relay, bone-conduction feedback hardware: not started. Persisted analytics: see session logging above (partial — verdict metadata only, not full analytics).

## Known gap: the voice heuristic may not generalize to the on-board mic

Diagnosed on the previous firmware implementation and **re-confirmed on the new PlatformIO firmware** 2026-08-21/22 (real hardware cycles consistently returned `voice_liveness_score` around 0.05–0.40 with `spoof_detected: true` for genuine speech): real, confirmed-uncorrupted speech captured on the physical XIAO ESP32-S3 Sense mic reads with `high_frequency_ratio` far below the heuristic's thresholds in `analyze_voice_liveness` (`utils/anti_spoofing.py`) — those thresholds were implicitly calibrated against whatever mic was used during earlier browser-based testing, which has a much wider frequency response than this board's PDM mic. As currently weighted, this makes it mathematically close to impossible for this specific mic to score "genuine." Deliberately not fixed by lowering the thresholds — `/voice-check` is shared with the browser demo path already validated against a documented case log, and lowering the bar risks that path unvalidated. This is a backend/heuristic-level finding independent of which firmware captures the audio — documented as a finding motivating the next phase: replacing hand-tuned heuristics with models fine-tuned on established datasets (ASVspoof, FaceForensics++, SIDTD) — mentor-endorsed approach, not training from scratch. Explicitly **not attempted** this phase despite being on the roadmap: swapping in a real trained model (for both the firmware and frontend paths) and on-device TinyML feature extraction were deliberately deferred the night before the panel to avoid destabilizing the now-working voice pipeline — see git history/session log around 2026-08-22 for the reasoning.

**Update 2026-08-22, later same day:** on-device TinyML (see the build-status bullet above) is now scaffolded, but it does **not** fix this gap — it's trained on fabricated synthetic signals (`ml/generate_synthetic_dataset.py`), not real audio from this mic, and is wired through as informational-only specifically so it can't interfere with `analyze_voice_liveness`'s already-validated (if miscalibrated-for-this-mic) behavior. Fixing the actual mic-mismatch bug still needs either real ASVspoof-style training data or — more directly useful, since it'd be calibrated for the exact mic in question — labeled genuine/spoof recordings captured from the real board and dropped into `ml/data/` per `ml/README.md`'s retraining instructions.

## Detection logic is still heuristic, not learned

`/face-check`, `/voice-check`, and `/document-check` classify liveness/spoofing/tampering using hand-tuned signal-processing thresholds (FFT ratios, Laplacian blur bands, ELA std-dev cutoffs) rather than models trained on labeled spoof/genuine data. No EER/FAR/FRR evaluation exists yet. Only the identity-*matching* piece (`/face-to-id-sync`, via DeepFace/Facenet) is a validated trained model. This is the headline item in the mid-sem report's Future Work (Ch. 5.4).

## Working in this repo

- Backend venv: `backend/.venv` (Windows: `.venv\Scripts\python.exe`). Install via `pip install -r backend/requirements.txt`.
- Run the backend: `cd backend && uvicorn app:app --host 0.0.0.0 --port 8000` (bind to all interfaces, not just localhost, if testing against real hardware on the same network). **Always verify with `netstat -an | grep ":8000.*LISTENING"` that it actually bound to `0.0.0.0:8000` and not `127.0.0.1:8000`** — confirmed this phase that restarting via some IDE "run" actions defaults to localhost-only silently, which looks fine locally but is completely unreachable from the board (`HTTP -1`/connection refused on the firmware side) until caught and restarted correctly. A Windows Firewall inbound rule for port 8000 is also needed if the network is categorized "Public" (`New-NetFirewallRule -DisplayName "FraudDetection Backend 8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow` — this is a system-security-setting change, ask the user to run it rather than running it directly). Frontend: `cd frontend && npm run dev` (port 5173, Vite).
- After touching any route or `utils/anti_spoofing.py`/`utils/scoring.py`, re-run `python backend/test_api.py`.
- `backend/uploads/` (and any subfolder under it) must stay empty between requests. `backend/debug_recordings/` and `backend/session_log.db` are allowed to accumulate (both gitignored) but aren't part of the fresh-analysis identity-check path.
- Firmware hardware testing: use a personal Wi-Fi hotspot, not institutional Wi-Fi — client/AP isolation and weak signal on institutional networks (confirmed again this phase, RSSI as low as -94dBm on one network) caused real, confirmed connectivity failures. Also disable any VPN/proxy client (e.g. Cloudflare WARP) on the dev machine — it was the confirmed root cause of a long stretch of "random" download/network failures earlier this project.
- Firmware build/flash/monitor: `cd firmware && pio run -t upload -t monitor --upload-port COMx` (combined target avoids missing early boot output from a gap between separate upload/monitor invocations). Opening a **new** monitor session resets the board (DTR/RTS auto-reset) — don't reattach one just to check status if you don't want to interrupt an in-progress cycle. On Windows, PowerShell/cmd may need `PYTHONIOENCODING=utf-8` set before the `pio` invocation, or `esptool`'s progress-bar output can crash a background echo thread with a `UnicodeEncodeError` and silently hang the whole upload (confirmed this phase — looked like an unrelated timeout at first).

- The current report is `Fraud_Detection_Smart_Glasses_Mid_Sem_Report.docx`/`.pdf` at repo root, built from `tools/generate_report.js`. Superseded drafts and the original `.doc`/`.docx` format template live in `archive/` — reference only, not live docs.
